单用户 · 请求体(T0–T3)随多轮对话的缓存变化

每一轮：harness 重新拼接 T0–T3 → 经 LiteLLM 转发厂商。色块下方标注该层的缓存命中状态。仅单用户视角。
层级颜色 T0 系统提示 T1 KB 前缀(pin) T2 对话历史 T3 当前消息
动作图例 WRITE 新写缓存 HIT 命中缓存 MISS→WRITE 过期重付 — 不缓存(每轮重发)
断点位置：断点①在 T0 后，断点②在 T1 后。缓存只认"断点之前"的内容 → T0、T1 可命中；T2、T3 在断点②之后，永不缓存。
三个铁律：① T0 段在 TTL 内几乎永远 HIT——它是全局固定系统提示，断点①前缀逐字节相同；仅首次是纯 WRITE，D/E 因 TTL 过期才 MISS→WRITE（T0 极小、成本可忽略）。 ② T1 段命中与否取决于 T1 内容是否变化且未过 TTL——切换/晋升/压缩 T1 即触发 WRITE。 ③ T2/T3 永远"不缓存"——它们在断点②之后，每轮重发但不入缓存，其变化不触发任何重记。

请求体解剖（一次调用的 messages 结构）

T0 系统提示⛓断点①
角色 system：固定指令、工具使用规范、全局项目索引
T1 KB 前缀⛓断点②
角色 system：当前 pin 的子项目知识库全文（recency_index 决定）
T2 对话历史
角色 user/assistant/tool：逐轮累积的历史 + 工具返回结果（断点②之后）
T3 当前消息
角色 user：本轮用户新问题（断点②之后）
另有独立顶层字段：tools（grep/read 等工具定义）、cache_control（加在 T0、T1 末尾的断点标记）。

H 单轮内 Agent-loop（工具调用）

用户一条消息，模型内部调 grep/read 3 次 = 3 次独立模型请求。每次 T0+T1 相同 → 全 HIT。

3 次请求 T0+T1 全命中 → 比「一次超长请求」更省。每次模型调用都是独立请求，共享稳定前缀即共享缓存。
规则应用：① 项目跳跃晋升 = T1 宽裕直接提 / 满则放 T2 / 连续 2 次提及强制提；② recency_index 跨会话持久化（同用户）。缓存为内容寻址 + TTL 短期，单用户视角。
