# 05 · 上下文与缓存机制

> 本文是 harness 封装里**最该显式处理**的部分。前提：已读 `01`（无状态函数、memoization）、`02`（职责分层）、`04`（harness）。

---

## 5.1 核心事实：模型 API 无状态

- 模型**没有 session**。每次调用独立，你每轮都把 `System + 历史 + 工具结果 + 当前消息` **完整重发**。
- "多轮连贯"是 **harness（agent 层）重发历史** 制造出来的——状态在 harness，不在模型、不在网关。
- 不止 system prompt，还含**完整历史与工具返回**才是连贯来源。

## 5.2 缓存是厂商 API 特性，不是 prompt 文本能实现的

- 前缀缓存靠厂商的缓存参数（Anthropic `cache_control` / OpenAI 自动前缀缓存 / 国内各家类似），**要求请求前缀 token 逐字节稳定**。
- 不缓存 → 每轮按**全量上下文**付费。知识库 agent 上下文长（10 万 token 级别），这笔钱很大；缓存后稳定前缀只算一次且打折。

## 5.3 谁控制缓存：你放断点，厂商执行

| 类型 | 模型 | 你如何控制 |
|---|---|---|
| 显式型 | 通义千问、智谱 GLM | 在 messages 里写 `cache_control:{"type":"ephemeral"}`，置于想缓存的前缀末尾（单请求最多 4 个断点） |
| 自动型 | DeepSeek、OpenAI | 不用写标记，厂商对重复前缀自动缓存（≥1024 token 阈值） |

**关键约束**：缓存永远是"从请求开头起的连续前缀"——你不能只缓存中间某段。断点之前的所有内容一起被缓存。

## 5.4 分层前缀 T0–T3（缓存最优结构）

```
[T0 System]        → 全用户相同、极小、永远不变 → 跨用户共享缓存
[T1 KB 上下文]     → 每用户/租户相同、重型 → 仅该租户内共享缓存
[T2 历史+检索片段]  → 每轮变 → 不缓存（放断点之后）
[T3 当前消息]      → 每轮变 → 不缓存
```

- **稳定块必须在最前**（T0、T1），可变块（T2、T3）放最后。
- 放**两个断点**：T0 后一个、T1 后一个 → 用户切换子项目时 T1 变了，但 T0 块仍命中。
- 断点**每轮都要带**（厂商不记忆你的偏好）。

## 5.5 多租户缓存：内容寻址天然隔离

- 缓存按**前缀 token 序列**寻址，不是按用户隔离。
- User A 和 B 的 `System` 相同 → 命中同一份（跨用户共享，但 System 才 1–2K，收益小）。
- **KB 不同 → 缓存键不同 → 天然隔离**，不需要特殊隔离逻辑。重型 KB 的缓存价值在**同一用户多轮复用**（聊 10 轮，KB 只付 1 次写入 + 9 次微小后缀）。
- **单中央 Key 反而最优**：所有虚拟 Key 翻成你的中央 Key → 缓存池统一，相同前缀跨用户最大化共享。

## 5.6 重型 KB 的 recency 压缩（与 Kimi K3 同构）

当上下文触及上限（如 512KB ≈ 15–18 万 token），按**新鲜度梯度**压缩：

```
全文(活跃子项目) → 摘要(较旧) → 仅索引(很久前提及)
```

- 保留**最新提及知识的完整性**，压缩时间间隔久的。
- **压缩会重置该块缓存**（内容变了，前缀不匹配，重写一次），但净收益正（上下文变小，后续每轮都便宜）。
- TTL 驱逐：缓存空闲 ~5–10 分钟过期。低频用例（测试期）红利小，**架构先埋好**，生产高频才显著。

> **和 Kimi K3 的关系**：K3 的 KDA（Delta Attention）把历史压进固定状态矩阵 ≈ 你的 recency 压缩；MLA 全局精读 ≈ 你的 T1 全文 pin；3:1 配比 ≈ "稳定缓存为主 + 偶尔全量重读"。区别仅在层级：K3 是模型内部、harness 是调用层，互补不冗余。
