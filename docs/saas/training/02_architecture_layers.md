# 02 · 架构与职责分层

> 本文讲清"云 SaaS / LiteLLM 网关 / opencode harness"三件套**各管什么**。职责边界乱了，后面缓存、计费、隔离都会出问题。

---

## 2.1 三件套总览

```
┌──────────── 用户机器（Local-First）────────────┐
│  产品 UI (你封装，不暴露终端)                    │
│     └─ opencode / mimo harness  ← Agent 层      │
│           · 上下文/记忆/工具(glob,grep,read)    │
│           · 注入 cache_control 断点             │
│           · 调模型(免费模型 或 你的网关)         │
└───────────────────┬────────────────────────────┘
                    │ 仅同步 KB(markdown) + 账号/计费信息
┌───────────────────▼────────────────────────────┐
│  你的云端 SaaS                                  │
│  账号 · Markdown 知识库存储 · 钱包/套餐         │
│     └─ LiteLLM 网关  ← 无状态路由/计费          │
│           · 统一国内厂商接口                     │
│           · 虚拟 Key / 预算 / 计量              │
│           · 透传 cache_control                  │
└────────────────────────────────────────────────┘
```

## 2.2 逐层职责表

| 层 | 负责 | 不负责 | 状态 |
|---|---|---|---|
| **云 SaaS** | 账号、Markdown 存储、钱包/套餐、虚拟 Key 管理、开通流程 | 推理、对话上下文 | 有状态（数据库） |
| **LiteLLM 网关** | 路由、计费、预算拦截、多模型统一接口、cache 透传 | 对话、记忆、工具、KB 检索 | **无状态** |
| **opencode harness** | Agent 循环、上下文拼接、记忆、工具调用、KB 检索、cache 断点注入 | 推理（转发给模型） | 有状态（本地 session） |
| **厂商 Provider** | 实际推理 | 任何业务逻辑 | 无状态 |

## 2.3 为什么这样切（关键认知）

1. **LiteLLM ≠ Agent**。它是**网关**，每次请求独立，不存对话、不管记忆、不检索 KB。把它当"API 网关/适配器"理解即可。
2. **上下文与记忆由 harness 管，不是网关**。多轮连贯、缓存前缀稳定性、压缩——都是 opencode（agent 层）的职责。
3. **账号/钱由云管**。充值、套餐、计量全在后端 + LiteLLM 数据库；客户端只持一个虚拟 Key 字符串，用户无感。

## 2.4 一次完整调用的数据流

```
用户提问
  → UI 发给本地 harness(opencode)
  → harness 拼 [System + KB + 历史 + 当前] + 打 cache 断点
  → 若付费：harness 带用户虚拟 Key 请求你的网关(LiteLLM)
  → 网关鉴权/查预算 → 转发厂商(DeepSeek/智谱/通义)
  → 厂商返回 text + usage(真实 token 数)
  → 网关按 pricing 算花费记到该虚拟 Key
  → 返回 harness → 解析 → 回 UI
  → 后台读 spend → 扣用户钱包(真实花费 × markup)
```

## 2.5 实施人员要守住的边界

- **别在网关里写业务逻辑**（检索、拼接属于 harness）。
- **别在 harness 里管钱**（计费/预算属于网关 + 云）。
- **客户端永远不碰 Provider 账户**（只持虚拟 Key）。
