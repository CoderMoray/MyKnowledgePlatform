## 2026-08-03 会话

### 本会话主线

从"T2 缓存命中优化"出发，逐层对齐：请求体物理顺序 → T1 内部三层结构 → 容量级联与评分机制 → 信号检测（非 RAG）→ 评分 vs 时间方案对比 → 蒙特卡洛模拟器可行性。

### 已定稿结论

**1. 请求体物理顺序（终版，推翻早前"L0 靠后"）**

```
[T0] ① [L0 全文] ② [L1 摘要] [L2 索引] [T2 frozen] ③ [T2 recent] [T3]
```

- 原则：**昂贵在前、易变靠后**。L0（全文，最贵）紧贴 T0，受断点②保护；L1/L2 变动只烧小尾巴，不杀 L0 缓存。
- 推翻 15:06 版"L0 放最后"：那个结论假设只有 L0 会变；实际 L1/L2 也会变（压缩/降级），若放 L0 前，L1 一变 → LCP 断在 T0 → L0 昂贵全文全重发。
- 断点：①T0 末 / ②L0 末 / ③frozen 末 = 3 个 + 1 余量（显式厂商上限 4）。DeepSeek 自动前缀无断点限制，只靠顺序。

**2. T1 内部三层语义**

| 层 | 内容 | 说明 |
|---|---|---|
| L0 | 知识全文 | **新知入口**——晋升时从 KB 源重读全文，不途经 T2、不是 L1 |
| L1 | 压缩摘要 | 旧块降级形态（L0 超限时最低分项压缩入此） |
| L2 | 索引+描述 | 全文**按需 read**（harness 预读 + 工具兜底 + 自愈晋升） |

- 纪律：**追加靠后 / 驱逐靠前 / 禁止中间插入**（L0 内部同样适用）。
- 容量级联：L0 超限 → 最低分压缩入 L1；L1 超限 → 降级 L2���L2 超限 → 剔除最早。
- 上限：L1 = token 上限（每块 ≤2K，总量 = 120K − L0 实际）；L2 = 条数上限（默认 50）。

**3. 命中语义**

- 尾部截断 → LCP 部分命中（新 L0 是旧 L0 的前缀，剩余项仍命中）。
- 中间删除 → 整段重写一次（压缩/驱逐稀有，可接受）。
- 压缩事件 L0 也少一条 + L1 加一条；因 L0 在前，只烧 L1 之后，L0 剩余项保住。

**4. 知识重要性评分（v1 设计）**

- `score = w1·频率EMA + w2·时效衰减 + w3·完整性需求`（权重待扫）。
- 使用频率：EMA（半衰期 H 轮，O(1) 增量）；"命中"= query 提及（词法）+ 工具调用落点 + harness 预读。
- 跨会话：`ema_freq + last_access` 持久化（recency_index 已定），`dwell_rounds` 会话内重置。
- 时效衰减：纯时间戳函数 `recency = 0.5^((now−last_access)/τ)`，τ≈1h；**不从提问文本推断**。
- 完整性需求：静态启发（代码块/表格/精确参数/API 规格占比高 → 高），可选 query 动态增强；作用是频率的反向权重（"老而重要"留 L0）。
- 知识量：pin 集合选择（评分排序 + cap M），**无 RAG 阈值**。

**5. 信号分层（知识库非 RAG）**

- 架构澄清：无 embedding/向量库/相似度检索；访问 = pin 全文 + 工具调用（grep/read）+ harness 预读。
- 晋升证据（谁进 L0）：工具调用日志（铁证，未 pin 才触发，无悖论）+ 词法。
- 圈内维持证据（L0 里谁还在用）：工具信号天然哑火（成功即无声）→ 词法 + **连续性启发**（无词法命中 → 延续上轮主题，抓"那个/它/继续"）+ **事件级 LLM 仲裁**（驱逐时刻，低频，成本 <1%）。
- 自愈回路：误压到 L1 → 全文离开上下文 → 用户再问必触发工具 → 信号复活 → 重晋升。误压代价 = 一次质量下降/一次重取，非永久错误。

**6. 评分 vs 纯时间顺序（缓存命中角度）**

- 稳态命中率**打平**（都由"驱逐位置"决定，不由"选择策略"决定）。
- 评分真实赢点：① 长程命中率（避免"驱逐→重访→重晋升→再 WRITE"）；② 内容价值/答案质量（同样预算装更重要的知识）。
- 正确姿势：**时间骨架（尾部追加，绝不按评分重排）+ 评分只做驱逐选择器 + 评分含时效衰减**（驱逐偏向尾部 → 缓存友好）。
- 工程建议：测试期（7–8 人低频）可先用纯时间方案，评分留接口后续上。

**7. 蒙特卡洛模拟器（可行性已确认，未实现）**

- 四模块：输入生成器（7 场景加权混合：冷启动/同项目多轮/项目跳跃/长期回归/新会话/压缩/Agent-loop）→ 缓存模拟器（LCP+TTL+计费+压缩调用成本）→ 策略对比（score/time/LRU）→ 输出（总成本/命中率/整段重写次数/质量代理=L0 全文在位率）。
- 四个未知量全参数化：输入分布（场景权重）/ 评分设计（参数族 w + 预测能力 ρ + 驱逐落尾概率 p_tail）/ 厂商语义（部分命中 on/off、TTL、1024 阈值、写价）/ 压缩质量（压缩比）。
- 输出是**决策边界**不是预测（如"重访率>X 且 空闲<Y 时评分赢"）；测试期真实日志校准。
- 信号建模：p_detect 分两态（pinned ≈0.6–0.7 / unpinned ≈1.0）+ 自愈回路动态 → 决定要不要上 LLM 仲裁层。

## 2026-08-06 会话

### 本会话主线

评估外部工具 **headroom**（LLM 上下文压缩层，chopratejas/headroom，本地实测版 0.33.0）是否作为缓存方案的补充。结论：**契合、暂不实施，作为补充方案记录**（详见 `caching-design.md` §14）。

### 评估结论要点

1. **定位**：headroom 是本地运行的上下文压缩层（压缩不调 LLM、数据不出域），不是存储/知识管理工具 → 与 MyKnowledge 平台本体定位不同，属 harness/工具层补充。
2. **与缓存设计同构**：其 CacheAligner（冻结稳定前缀、只压 live zone）与本文 T0–T3 + 断点设计理念一致；其本地压缩器可替代 §7 中"用一次模型调用做摘要"的 L1/L2 压缩环节（零模型成本）。
3. **MCP 集成可行且是官方主打场景**：headroom 提供 `compress_tool_result()` / `HeadroomMCPCompressor` / `MCPToolProfile`，专为压缩 MCP 工具输出设计。本项目读类工具（nav__get_document 等）为纯字符串返回，注入点干净。
4. **推荐集成形态（若实施）**：读类工具加 `compressed=False` 参数 + 新增 retrieve 工具（CCR 兜底）→ 由 AI 自行决定压缩/取回；list/find 高压缩、get_document 低阈值；修改前必须 retrieve 原文。
5. **关键风险**：① M 系列 Mac 压缩率 bug（issue #2742，需先实测）；② headroom-ai 依赖重（onnxruntime + litellm + 首次下载 ~400MB 模型），只能做 optional extra；③ 生产压缩率中位数仅 ~4.8%，需真实 KB + 中文 markdown A/B 验证；④ headroom 依赖 litellm 需验证与网关共存兼容性。
